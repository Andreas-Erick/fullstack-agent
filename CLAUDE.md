# Siren Assistant — notes for the agent modifying itself

(Formerly Nexus Agent. Internal identifiers keep the old name on purpose: the `NEXUS_*` environment variables, `window.nexus` in the renderer, `window.NexusAndroid`, the `nexus-agent` ping id the phone checks, `startedByNexus`, the Android package `com.nexusagent.android` and the appId `com.nexus.agent` (so installs upgrade in place). User-visible text says Siren / Siren Assistant.)

This file is read by the assistant (and Claude Code) before changing this codebase. Keep it accurate when the architecture changes.

## Shape of the app
Electron app, plain JavaScript, **no build step**. Node ≥ 22. Run `npm start` (dev mode with DevTools: `npm run dev` / `dev.bat`); syntax-check with `npm run check`.

- `main/` — Electron main process (CommonJS, Node APIs).
  - `main.js` window, `app://` protocol (serves only whitelisted folders, see `SERVED`), every IPC handler (`handle('ns:method', fn)`).
  - `llm.js` providers + agent tool loop: `openai` (FreeLLMAPI, SSE), `anthropic` (Anthropic SDK), `claude-code` (delegates to `claudecode.js`), `auto` (multi-provider: `router.js`).
  - `router.js` multi-provider mode: the user's ranked list (`routing.order`), smart per-task preference, cooldowns after rate limits / credit caps. Gemini, DeepSeek, Groq, Perplexity run through the OpenAI path via `router.concrete(settings, id)`. A turn falls back to the next provider only before any tool ran (no action runs twice); streamed text is retracted. `runTurn` returns `provider`, stored on the assistant message.
  - Switching brains by chat ("switch to a local model"): tools `brain_options` / `brain_switch` (`tools/brain.js`, group `brain`; `brain_switch` is in `COMPACT_TOOLS` so a small local model can switch back) over the pure `braincore.js` (`CHOICES`, `patchFor`: writes only `llm.provider` and that brain's model; a local model's `baseUrl` comes from `localmodels.detect()`, never from the caller; `test/braincore.test.js`). Any router provider id can be `llm.provider` on its own (`llm.narrow`); Settings, the brain pill (`SINGLE` in `app.js`), the HUD and Health handle those ids too.
  - Local brains: `localmodels.js` (`detect()`: Ollama and LM Studio on localhost, `llm:localModels`) over the pure `localcore.js` (model sizes, suggestions, `compactWanted`, `COMPACT_TOOLS`); `llm.runOn` gives every local model (auto; not only small ones: all tools are ~25k tokens a local model re-reads each message) `prompt.buildCompact` (the persona as `personacore.forSmallModels`: a master prompt of `SUMMARY_FROM` characters or more as its short version `agent.personaSummary` = `{ text, for, by }` (persona-synced; written once per master-prompt fingerprint by the user's own local model, `persona.ensureSummary`, triggered from `main.js` after start and after persona/brain changes; `by: 'user'` is never replaced; Persona studio row), else `personacore.digest` (identity, the style section, up to three sample lines); the memories matching the message first (`relevantMemories` `always`, real shared words only: `sharesWord`), or a line saying none match; short rules that ask for the persona's voice, examples, the key rule repeated at the end) and only `COMPACT_TOOLS` (setting `llm.compactPrompt` auto|on|off; `test/localbrain.test.js`). Tools on request: the compact path also offers `tools_more` (`tools/toolbox.js`, group `toolbox`, never in the full prompt) for the groups in `localcore.TOOLBOX`; `localcore.hintGroups` preloads obvious ones; loaded groups stay in `conv.toolGroups` and follow the everyday tools (`compactTools`), and `runOpenAI` rebuilds the tool list each round from `ctx.toolset`. Hand-over (`llm.handOver`, off by default, user-only, `test/handover.test.js`): `llm.runSingle` sends a local brain's message to the Claude brain (claude-code, else anthropic, when ready) straight away for `localcore.handOverHint` (code work, a connector by name, a long text), or when the local model calls `hand_over`; a routine (`runTurn` `routine`) that names a connected service (`localcore.neededService`) goes to Claude even with the setting off, and a routine's text never counts as engineering (it gets the larger round budget only) (offered only then; never after a tool that isn't `localcore.isReadTool` ran in the turn: `ctx.wrote`); the local text is retracted and a notice says so. A first reply that gives up without a tool (`localcore.gaveUpUnlooked`) is retracted and the model is asked once to look (`LOOK_FIRST`; kept out of the stored turn). `localcore.requestExtras` adds `keep_alive: '30m'` and, unless the pace is deep, `reasoning_effort: 'none'` to local requests (`runOpenAI` retries without them on a 400). Router provider `local` (settings `local.*`, ready when a model is set, first for quick spoken replies).
  - `screenshare.js` screen sharing (desktopCapturer thumbnails): started/stopped only by the user; `capture()` gives a JPEG data URL. Images reach the model as `images` on `runTurn` and as `__image` in tool results (`look_at_screen`); `stripImages` keeps them out of stored conversations.
  - `persona.js` + `personacore.js` personas: the live `agent.*`, `appearance.*`, `ui.face`, `voice.voice`/`localVoice` settings are always the active persona; `store.setSettings` copies them into its entry in `personas.list` on every save (`personacore.sync`), and a switch (`persona:switch`, tool `persona_switch`) swaps another one in. Code that reads the name, prompt, theme or face needs no persona logic. The agent changes its own look with `theme_update` (validated by `persona.themeChange`) but can't create personas or edit master prompts. The scene behind the face (`appearance.scene`, `{ svg, caption }`, persona-synced): `persona.generateScene` asks the model for one SVG with the prompt in the pure `scenecore.js`, whose `cleanScene` strips everything that runs, loads or references outside (scripts, handlers, images, uses, styles, filters, links, animation) and fixes the root's viewBox and crop; `renderer/js/scene.js` cleans it again with DOMPurify's SVG profile and puts it into the `.face-scene` holders (Face view, chat face panel); `styles.css` drifts its `#far/#mid/#near` layers and dims it under `body[data-agent='sleeping']`. IPC `persona:scene`; drawn after "Generate look & feel" and by the Persona studio's "Scene behind the face" row.

Tools `learning_*`, `vocab_*` (group `learning`, needs the vault) and `language_practice` (sets `learning.practiceLanguage`: speech recognition and the voice switch language, see `renderer/js/practice.js`). The teaching method is `teachingBlock()` in `prompt.js`; the tracker summary goes into the stable prompt, practice mode into the per-turn context. `personatemplates.js` ready-made personas (STEM tutor, polyglot coach).
  - Flashcards (rail "Cards", `renderer/js/flashcards.js`; the phone's More → Flashcards in `renderer/remote/screens.js`, cards drawn by `cardMarkdown` in `renderer/remote/app.js`, which keeps only `data:` images and sounds): `flashcards.js` (vault I/O, deck ids `f:<note>` and `v:<language>`, studied-today counts in `<userData>/flashcards-days.json`, undo of the last answer per deck, media inlined as data URLs) over the pure `flashcore.js` (`Flashcards/<Deck>.md`: frontmatter options, one block per card starting `<!-- card {json} -->`, front `?` back; `Front :: Back` lines and cloze blocks typed by hand are completed on the next write; the queue with Anki's daily limits and learn-ahead) and `ankicore.js` (Anki's scheduler: SM-2 as Anki v3 runs it, with learning steps, fuzz, lapses, leeches, 4 am rollover; FSRS-5 with Anki's default parameters as the deck option `scheduler: fsrs`). Vocabulary decks (`srs.js`) are scheduled by `ankicore` too: their comment keeps `type/step/at/last/s/d`. Imports: `flashimport.js` (I/O; Anki packages via `node:sqlite` from a temporary copy) over the pure `flashimportcore.js` (CSV/TSV/Anki text, HTML → Markdown, Anki templates, zip, zstd and the bits of protobuf of the newest packages); files only through `documents.resolveAllowed` (the workspace and allowed folders, or a file the user picked); media into `Flashcards/media/<Deck>/`. Tools `flashcards_*` (group `learning`). Mixed learning (interleaving): `flashcards.js` `mixStart/mixNext/mixAnswer/mixUndo` run sessions in memory (mode `due`: every deck's own queue, the next deck by the pure `mixcore.pickDeck`, never the same twice while another has cards; mode `all`: every card shuffled by `mixcore.interleave`, practice that writes nothing), one operation at a time per session, answers carry the shown card id; IPC `flashcards:mix*`, phone `/api/data/flashcards/mix*`, tool `flashcards_mixed`. Hand-typed cards get ids from their text (`flashcore.textId`), stable across reads; `answer()` ignores a repeat of the same card within 800 ms (double tap). The skill tree's `deck` sources count every flashcard and vocabulary deck by name (`skilltree.evidence`).
  - Habits: `habits.js` over the pure `habitcore.js` (`Habits.md` in the vault: habits with a weekly target in `<!-- habit … -->` comments, a dated log; streaks and weekly stats). Tools `habit_*` (group `habits`, needs the vault), the Habits view (`renderer/js/habits.js`), a per-turn line in `prompt.turnContext`. Coaching guidance is `coachingBlock()` in `prompt.js`.
  - Skill tree: `skilltree.js` gathers the evidence (learning topics, deck maturity, habit consistency) for the pure `skilltreecore.js` (`Skill Tree.md`: one line per skill with a JSON `<!-- skill … -->` comment: area, needs, from, goal; a goal's needs are its steps and its progress adds up from them; no cycles; progress and states computed, never stored; the constellation layout). Tools `skilltree_*`, the Tree view (`renderer/js/skilltree.js`, SVG).

Tools `stream_*` (group `stream`, setting `memory.stream`); `prompt.turnContext(…, { query })` adds "Recalled from your memory stream" for the user's message (`llm.runOn` passes it).

## Conventions
- Match the surrounding style: 2-space indent, single quotes, semicolons, small focused functions, short comments only where they add context.
- New setting: add a default in `store.js` `DEFAULTS`, a control in `renderer/js/settings.js` (`text()`, `toggle()`, `select()` helpers bind to `section.key` paths and auto-save).
- New tool: add it to its group file in `main/tools/` (a new group: a new file, listed in `TOOLS` in `main/tools.js`) with a clear description; give it a label in `TOOL_LABELS` in `renderer/js/chat.js`.
- New view: rail button + `<section>` in `index.html`, a module with `init*()`/`refresh()`, wire it in `app.js`.
- Renderer-only changes need a window reload; `main/`, `preload.js` or `package.json` changes need an app restart.
- New npm dependencies can't be installed by the agent; ask the user to run `npm install <pkg>`.

## Engineering method, checks and tests
- `docs/ENGINEERING.md` is how to change this app well: the loop (understand → design → plan → implement → verify → review → commit → learn), design principles, cross-file checklists, security review, tests, debugging, definition of done. Read it before anything beyond a small fix.
- `npm run check` = syntax of every file, then `scripts/verify.js`: integrity across files (IPC handler ↔ preload channel ↔ renderer `api.*` call, relative imports/requires and the names they import, settings keys bound in Settings or in `SETTABLE` exist in DEFAULTS, unique tool names; tool labels as a warning). It reads the code statically through `main/codemap.js` (also behind `code_map` / `code_outline`).
- `npm test` = `test/*.test.js` with Node's built-in runner (no dependencies, offline, a few seconds). `test/modules.test.js` loads every `main/` module with an Electron stand-in and checks every tool's schema, so load-time mistakes fail the tests, not the app's start. Load main modules with stand-ins via `test/helpers.js` (`stub`, `load`, `fileStore`). New logic gets tests; a bug fix gets a regression test.
- `selfchange.commit` (and so every self-change) records a change only if check and tests pass, then marks it pending; after the next restart/reload `verifyAfterLoad` checks the log (`main/errorinsight.js` groups problems) and reports problems to the user, the agent's context (`prompt.turnContext`), Health and Evolution.
- `npm run eval -- --brain <brain> [--brain …] [--only id,id] [--out file.json]` (`scripts/eval.js`, cases in `scripts/eval-cases.js`): the assistant's test set against real brains (`local:<model>[+deep:<model>][+handover]`, `claude:<haiku|sonnet|opus|auto>`), in Electron without a window on a throwaway data folder and a made-up vault (dates relative to today), each case a real `llm.runTurn` checked on what really happened (the vault afterwards, the tools used). Claude runs count toward the user's plan; not part of `npm test`. Add a case when a real conversation goes wrong.
- `npm run smoke` (`main/smoke.js`, flag `--smoke`): a real start on a throwaway data folder (`NEXUS_USER_DATA`), waits for the window's `app:ready`, opens every rail view once, then resizes the window through common windowed sizes and fails if the title bar's fold changes after settling, its content is cut off, or a layer transformed past its edge folds it (`STEADY`; `fitTitlebar` measures content, never `scrollWidth`, which the HUD scan line inflates); fails on console errors, crashes or main-process exceptions; no servers or helper apps start. It also fails on text cut off or spilling out of its box (`renderer/js/cliptest.js` `findClippedText`; a deliberate "…", line clamp or fade mask is fine, `data-clip-ok` opts out): every view at 1600×1000 and 900×600, every approval shape, the secret and recording prompts (`PROMPTS`, sent as from the main process), and a seeded conversation with a long link, token, wide table, code and formula (`seedChat`); the browser test runs the same check on every phone/tablet screen and an approval card. `test/approvalkinds.test.js`: every approval kind has a heading on desktop and phone. For design work, `NEXUS_SHOTS=<folder>` saves a PNG of every view (still, `fx-still`) plus the scenes in `NEXUS_SHOTS_SCENES` (JSON `[{ name, js, wait }]`); the browser test takes the same variable for every phone/tablet screen. `npm run test:browser` also runs `*.browser.test.js` (skipped in `npm test`): `test/browser/remoteclient.js` is an Electron main script that pairs with the real companion server and opens every phone-client screen at phone and tablet sizes (console errors and blank canvases fail). Both run in `release.yml` before publishing.
- Turn pace (`main/pace.js`, pure, `test/pace.test.js`): each message is classified locally as quick (lookups in the user's own things, small commands, greetings → fast model, effort low), deep (explain/why/compare/plans/code → mode 'deep': the provider's `deepModel`, the main model when empty; raises an explicit low/medium effort) or normal (→ mode 'normal': `claudeCode.normalModel` / `anthropic.normalModel`, Sonnet by default, in `llm.effectiveModel`). Applied in `llm.runOn`: Claude Code changes model (`set_model`) and effort (`apply_flag_settings` `effortLevel`, `Session.setEffort`) on the live session; the Claude API uses `ctx.effort` in `turnEffort`. Setting `llm.autoPace`; an explicit `llm.modelMode` other than default turns it off.
- Engineering mode (`main/engineering.js`): coding, self-change and debugging turns get `llm.engineeringToolRounds` (40) tool rounds and at least "high" effort on the Claude API; a turn that starts a self-change is upgraded mid-way.

## When something is broken
Read `TROUBLESHOOTING.md` (→ Reading the log), run `analyze_errors` (distinct problems with code locations) and `diagnose`, read the log (`read_app_log` with the failing line's `turn` id) — then fix the cause, with a regression test.

## Logging (`main/logger.js`)
- `log.info|warn|error(event, data)`: short event name, details as an object. Pass the Error object itself (`{ error: err }` or as data), not `err.message`: the logger keeps message, code, cause and stack.
- Work that belongs to a turn runs inside `log.withContext({ turn, conv })` (set in `main.js` `chat:send`; tools get it through `ctx.logTags`, Claude Code output through `Session.inTurn`). New async entry points should do the same.
- Never log secrets or whole documents/prompts; the logger masks known key formats, but don't rely on it. `log.debug` only writes when debug logging is on.
- Renderer code logs through `logEvent(level, event, data)` (lines appear as `ui: …`).

## Safety rails (do not remove)
- `approvals.js` gating, the external-content notice in `tools/common.js` (applied in `tools.js`), the `SETTABLE` allowlist (the agent can't change safety/permissions/code access/secrets), and the standing rules in `prompt.js`.
- `selfchange.js` records every change in git; `scripts/recover.js` undoes the last change if the app no longer starts.
- Crash safety nets (see TROUBLESHOOTING.md → Crashes and recovery): the per-file write queue and settings backup/recovery in `store.js`, the per-child handlers and start-failure retry in `claudecode.js`, the speech-to-text timeout/reload and playback time limits in `renderer/js/voice.js`, window-crash reload in `main.js`.
- Path checks in `files.js`/`codebase.js`/`documents.js`, the private-network block in `websearch.js`, and the IPC surface in `preload.js` protect the user — keep them.
- `companion.js` / `tunnel.js`: the Host/Origin checks, the Cloudflare Access verification, the tunnel token kept out of the command line and logs, the "Remote" pill's one-click off, token check on every route, the approval-id allowlist (`openApprovals`: secret and recording prompts share the pending map and must never be answerable remotely), and the narrow route list. Never add settings, secrets, tools or arbitrary files to it: the phone's data screens go only through `companiondata.js` (trimmed copies; notes only inside the vault; the only writes are checking a habit off and answering a flashcard, with its undo) behind `remote.shareData` (user-only); the village's code and art are served from fixed lists (`STATIC`, `WORLD_ART`).
- `helperapps.js` launches programs: their paths (`helperApps.*`) are settings only the user changes, never in `SETTABLE` (`test/helperapps.test.js` checks this), and only the two known apps can be started.
- Screen sharing starts only from the user's click (never from a tool), screenshots are tainted as external content and never stored; the PDF renderer keeps JavaScript off and the network blocked. See `PRIVACY.md` and keep it accurate when data flows change.

Signing secrets and pinned actions: see the header of `release.yml`; `security.yml` audits dependencies, `.github/dependabot.yml` proposes updates. `.github/workflows/release.yml` builds and publishes on a `v*` tag.
